# Case Study: flowgen-app — Natural language to rendered diagrams

Describe a flow in plain English ("OAuth login with refresh tokens") → Haiku emits
Mermaid syntax → it renders to an SVG in the browser. React + TypeScript, no UI
framework.

## The Problem

Turning a sentence into a diagram looks like one feature. It's actually two hard
problems wired in series, and the seam between them is where naive implementations
fail.

The first is getting a language model to emit strictly valid, renderable Mermaid.
Ask plainly and the model returns what's helpful to a _human_: a sentence of
explanation, a ` ```mermaid ` fenced block, maybe a closing note. A renderer wants
none of that — one stray fence or prose line and parsing fails. Because the model
is non-deterministic, the output has to be coerced back to raw syntax on every
response, defensively, not just hoped for via the prompt.

The second is rendering that output in the browser. The source is machine-generated
and may be syntactically invalid; the SVG it produces is untrusted markup about to
be injected into the DOM. Drop it straight into `innerHTML` and a malformed diagram
takes down the React tree, while a crafted node label becomes an XSS vector.

Both problems sit under a moving target: the user keeps typing and re-submitting.
Requests fire faster than the API responds and faster than the renderer draws.
Without ordering guarantees, a slow earlier response lands after a newer one and
silently overwrites it — the diagram equivalent of the collaborative editor's
silent document corruption.

## Key Technical Decisions

### Generation as an explicit state machine

The lifecycle of a request is modelled as a discriminated union rather than a
handful of loose booleans (`isLoading`, `error`, `data`):

```ts
type GenerationState =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'repairing'; error: string }
  | { status: 'success'; code: string; repaired: boolean }
  | { status: 'error'; message: string };
```

This makes impossible states unrepresentable — there is no way to be "loading" and
"error" at once, or to hold a `code` string while not in `success`. The UI switches
on `status` and renders each branch exhaustively, which is what kills the loading
flicker and stale-error glitches that boolean soup produces.

### Single-flight requests with AbortController

The naive approach fires every generation as fire-and-forget. Under real typing
speed, that means overlapping in-flight requests whose responses can return out of
order — and the slowest one wins, clobbering newer state.

Instead, each generation aborts the previous one. The active `AbortController` is
held in a ref; a new generation (or pressing **Stop**, or unmounting) aborts it
before starting the next, and any response whose signal is already aborted is
dropped rather than written to state.

```
generate("...")      ──▶ abort previous ──▶ new AbortController ──▶ API call
                                                  │
newer generate(...)  ──▶ aborts the in-flight one ┘   (its result is ignored)
```

Only the latest request can ever resolve into the UI. Aborts are treated as
intentional and never surfaced as errors.

### A stale-render guard around async rendering

The same race exists one layer down. Mermaid rendering is asynchronous, and the
diagram source can change again before a render resolves. The render effect captures
a `cancelled` flag in its cleanup; if the source changes mid-render, the superseded
result is discarded instead of being painted over the newer one.

```ts
let cancelled = false;
renderMermaid(code)
  .then((svg) => { if (!cancelled) setState({ svg, ... }); })
  .catch((err) => { if (!cancelled) setState({ error, ... }); });
return () => { cancelled = true; }; // a newer code value invalidates this render
```

The renderer hook is also called unconditionally and fed `null` until there's a
diagram to draw, so React's hook order stays stable across every state branch.

### Model output is untrusted by default

Two guards bracket the model's response. Before it ever reaches the parser, the
diagram is pulled out of any code fence (`` ```mermaid `` … `` ``` ``) and the
sentences the model sometimes adds around it, in case it wraps its answer despite
the prompt. A fence left open because the output hit `max_tokens` is handled too. And Mermaid is initialised with
`securityLevel: 'strict'`, so the SVG is sanitised before it's injected — the source
is generated by a model, not trusted.

Invalid syntax is expected, not exceptional, so the app repairs it (next section).
If a diagram still doesn't parse, `mermaid.parse` rejects with a readable message,
which is shown as a recoverable inline error next to the source. A top-level error
boundary catches anything that still slips through, so the worst case is a "try
again" message, never a blank screen.

### One automatic repair, driven by the real parser

A model that's right most of the time still sends back a diagram that won't parse
now and then: an unescaped `(` inside a node label, an arrow with no target. Telling
the user "invalid syntax, try again" makes them pay for the model's mistake, and a
fresh attempt can make the same mistake again.

Instead, every draft is checked with `mermaid.parse` before it's shown. If it fails,
the draft and the parser's own error message go back to the model in a second
request:

```
generate ──▶ draft ──▶ mermaid.parse ──┬─ ok ─────────────────────────▶ render
                                       └─ error ──▶ repair request ──▶ render
                                          (draft + "Parse error on line 2:
                                           ...A[Start (x)] --> B
                                           Expecting 'SQE', … got 'PS'")
```

The parser's message names the line and the token it choked on, so the model fixes
that line instead of starting over. A few decisions keep this cheap and honest:

- **At most one repair.** A second retry would mostly spend quota on diagrams the
  model can't get right. If the repair still fails, the user sees the parse error
  next to the source, and an **Auto-fixed** badge marks diagrams that needed a repair.
- **Same abort guarantees.** The repair runs under the generation's
  `AbortController`. Pressing **Stop** or starting a new prompt while the draft is
  being parsed cancels it before the second request is sent, so no quota is spent
  on a result nobody will see.
- **The broken draft is untrusted input.** It comes back from the browser, so the
  function sends it as tagged data inside a user turn (`<diagram>`, `<parse_error>`),
  never as a replayed assistant turn it could use to pose as the model's own output.
  It's length-capped like the prompt, and the parser error is truncated.
- **Testable without the network.** `generateDiagram` takes its model call and
  validator as arguments, so the retry rules are unit-tested with fakes. The
  request contract (`netlify/lib/diagram-request.ts`) has no SDK imports, so its
  validation and fence handling are tested without an API key.

### A constrained system prompt on the cheapest viable model

The system prompt narrows the model to exactly one job: output _only_ Mermaid, pick
the diagram type that fits the description, and never invent syntax that wouldn't
parse. Because the task is this tightly scoped, it doesn't need a frontier model —
it runs on `claude-haiku-4-5`, the lowest-cost, lowest-latency model in the family,
with a deliberately low `max_tokens` ceiling to bound cost and trim time-to-first
diagram.

### The API key stays behind a Netlify Function

The browser never talks to Anthropic. It posts a prompt to `/api/data`, a Netlify
Function that holds the key in a server-only environment variable — no `VITE_`
prefix, so Vite can't inline it into the bundle. The function also owns the model,
system prompt and token ceiling, so the endpoint can only turn a length-capped prompt
(plus, for a repair, a length-capped draft and its parse error) into a diagram. It
can't be repurposed as a free general-purpose LLM proxy.

Two guards protect the quota. A same-origin check stops other sites from calling the
endpoint through their visitors' browsers, and a per-IP rate limit, enforced by
Netlify before the function runs, caps scripts that forge the `Origin` header.

Locally, copy `.env.example` to `.env.local` and run `npx netlify dev`, because plain
`vite` doesn't serve the function. `npm test` runs the unit tests (Vitest).

### Lazy-loaded diagram renderers

Mermaid ships a separate renderer for every diagram type (flowchart, sequence,
state, ER, …), which is a lot of code. The bundler code-splits those out, so the
initial load stays lean and only the renderer for the diagram type actually
produced is fetched on demand.
